## Context

The CodeGraph CLI uses CAC (a lightweight CLI framework) for command parsing. When CAC encounters errors (unknown command, invalid flag, missing argument), it throws `CACError` with raw Node.js stack traces. The current implementation lacks error transformation, resulting in unfriendly UX for non-expert users.

**Current Error Flow**:
```
CACError thrown → Uncaught → Node.js prints stack trace → User confusion
```

**Desired Error Flow**:
```
CACError thrown → Caught at entry point → Error transformer → Friendly message → User understands
```

## Goals / Non-Goals

**Goals**:
- Transform CACError into friendly, actionable error messages
- Provide command suggestions for unknown commands
- Provide flag suggestions for invalid flags
- Add path format hints in scope/impact error messages
- Maintain JSON output compatibility (--json flag errors remain structured)

**Non-Goals**:
- Full error code system for all internal errors (focus on CLI layer only)
- Internationalization/localization of error messages
- Auto-correction of user inputs

## Decisions

### Decision 1: Error transformation at CLI entry point

**Choice**: Catch and transform errors in `bin/codegraph.ts` at the top level.

**Alternatives considered**:
- Per-command error handling: Rejected - too scattered, inconsistent handling
- Middleware approach: Rejected - CAC doesn't support middleware for errors

**Rationale**: Centralized handling ensures consistent error UX across all commands and avoids duplication.

### Decision 2: Error code classification

**Choice**: Define a small set of CLI-specific error codes (E_CLI_*).

**Error codes**:
- `E_CLI_UNKNOWN_COMMAND`: Unknown command entered
- `E_CLI_UNKNOWN_FLAG`: Invalid flag used
- `E_CLI_MISSING_ARG`: Required argument missing
- `E_CLI_TARGET_NOT_FOUND`: Target path not found (scope/impact)
- `E_CLI_INTERNAL`: Unexpected internal error

**Error code trigger locations**:
- `E_CLI_TARGET_NOT_FOUND`: Thrown by `scope.ts` and `impact.ts` when `getScope()`/`getImpact()` returns null
- `E_CLI_UNKNOWN_COMMAND`, `E_CLI_UNKNOWN_FLAG`, `E_CLI_MISSING_ARG`: Generated by `transformCACError()` from CACError parsing
- `E_CLI_INTERNAL`: Fallback for non-CACError or regex parse failures

**Rationale**: Structured error codes enable:
- JSON output consistency (`{ success: false, error: { code, message } }`)
- Programmatic error handling by downstream tools
- Clear documentation of error types

#### CACError Parsing Patterns

**Why regex patterns**: CAC error messages follow predictable formats. Regex extraction allows flexible parsing that survives minor CAC version changes, avoiding hardcoded string matching.

**Regex patterns for CACError message parsing**:
```typescript
const CAC_ERROR_PATTERNS = {
  // WHY: CAC outputs "Unknown command 'xyz'" when command doesn't exist
  UNKNOWN_COMMAND: /^Unknown command '(.+)'$/,

  // WHY: CAC outputs "Unknown option `--xyz`" for invalid flags
  // Note: CAC uses backticks and period at end
  UNKNOWN_OPTION: /^Unknown option `--(.+)`\.$/,

  // WHY: CAC outputs "Missing required argument xyz" for missing args
  MISSING_ARG: /^Missing required argument (.+)$/,
};
```

**Fallback strategy**: If regex fails to extract information from CACError message:
1. Log original error for debugging (JSON mode only)
2. Return `E_CLI_INTERNAL` with sanitized message
3. Include `error.debug` field in JSON output containing original error text

**This ensures users always see a friendly message, never a raw stack trace.**

### Decision 3: Path format hint injection

**Choice**: Add path format hint in scope/impact command handlers when target not found.

**Message format** (UNIFIED with specs):
```
Target not found: <user-path>
Hint: Use full path format: packages/<pkg>/src/<file>.ts
```

**Rationale**: Users often try relative paths like `src/analyzer/index.ts` when the actual path is `packages/codegraph/src/analyzer/index.ts`. A simple hint reduces confusion.

#### Path Format Validation Logic

**Why validation**: Not every "target not found" error needs a path hint. If the user already provided a valid monorepo path format, the hint is redundant and adds noise.

**Valid path format regex**: `^packages/[a-z-]+/src/.+\.ts$`

**Validation logic**:
```typescript
function shouldShowPathHint(userPath: string): boolean {
  // WHY: If path already matches monorepo format, suppress hint
  // The user knows the format; the file simply doesn't exist
  const VALID_MONOREPO_PATH = /^packages\/[a-z-]+\/src\/.+\.ts$/;
  return !VALID_MONOREPO_PATH.test(userPath);
}
```

**Behavior**:
- Path matches regex → suppress hint (file doesn't exist, but format is correct)
- Path doesn't match regex → show hint (user likely using wrong format)

#### Monorepo Detection Criteria

**Why detection**: Path hint format varies by project structure. Monorepo uses `packages/<pkg>/src/...`, single-project uses `src/...`.

**Detection logic**:
```typescript
function isMonorepo(projectRoot: string): boolean {
  // WHY: Simple presence check - 'packages/' directory is the monorepo marker
  // More complex checks (pnpm-workspace.yaml) add unnecessary complexity
  return fs.existsSync(path.join(projectRoot, 'packages'));
}
```

**Behavior**:
- Monorepo detected → hint uses `packages/<pkg>/src/<file>.ts` format
- Not monorepo → hint uses `src/<file>.ts` format (or suppress entirely)

### Decision 4: Error output routing

**Choice**: Route errors to stderr in text mode, include in JSON structure in JSON mode.

**Text mode**: Friendly message to stderr
**JSON mode**: Structured error object to stdout (matching existing pattern)

**JSON error structure** (UNIFIED with spec):
```typescript
{
  "success": false,
  "error": {
    "code": "<error-code>",
    "message": "<friendly-message>",
    "debug": "<original-error-details>" // WHY: Only in JSON mode for debugging
  },
  "durationMs": <execution-time-ms> // WHY: Total CLI execution time, not error occurrence time
}
```

**JSON mode detection**: Check `process.argv.includes('--json')` before error handling begins.

**Rationale**: Maintains consistency with existing cli-output-routing spec.

#### Suggestion Generation Mechanism

**Why document this**: Developers must know how to extract available commands/flags from CAC. Without this, they would reverse-engineer CAC internals.

**Mechanism**:
```typescript
function getAvailableCommands(cli: CAC): string[] {
  // WHY: CAC stores commands in cli.commands map
  // Extract names, filter built-in (help, version), sort alphabetically
  return Object.keys(cli.commands)
    .filter(name => !['help', 'version'].includes(name))
    .sort(); // WHY: Alphabetical sorting for consistent UX
}

function getAvailableFlags(command: Command): string[] {
  // WHY: Each command's options are in command.options array
  // Flags are command-specific, vary per command
  return command.options
    .filter(opt => opt.negate || opt.name) // Filter valid flags
    .map(opt => `--${opt.name}`)
    .sort(); // WHY: Alphabetical sorting for consistent UX
}
```

**Key insight**: Suggestions are **command-specific**. The `analyze` command has different flags than `scope`. Always extract flags from the specific command context.

## Risks / Trade-offs

**Risk**: CACError message format changes in future CAC versions
→ Mitigation: Extract key information via regex patterns with fallback to `E_CLI_INTERNAL` + raw message sanitization

**Risk**: Over-transformation hides useful debugging information
→ Mitigation: Include original error message in JSON mode via `error.debug` field

**Risk**: Path hints become outdated if project structure changes
→ Mitigation: Hints are generic (explain format, not specific paths)

**Capability scope clarification**: This `cli-error-handling` capability operates at the **CLI layer only**. It transforms CACError and CLI-level errors. Internal analysis-level errors (parsing errors, import resolution failures, analyzer exceptions) **pass through** wrapped in `E_CLI_INTERNAL` with original message preserved. This ensures analysis debugging information remains accessible while CLI UX stays friendly.
